# TH1520 / RevyOS backend

This backend targets LicheePi 4A and other TH1520 boards running the RevyOS multimedia stack. It does **not** require a V4L2 VPU driver. It uses the RevyOS-patched FFmpeg OMX decoders, which call Bellagio and the `th1520-vpu` VC8000D component.

## Supported configuration

- H.264 8-bit 4:2:0 and HEVC Main 8-bit 4:2:0, SDR.
- X11 desktop, EGL and OpenGL ES 2.0 or later. No DRM master or exclusive display ownership is required.
- Fullscreen or windowed output, aspect-ratio preservation and clockwise 0/90/180/270-degree rotation.
- Existing PulseAudio/ALSA audio and evdev/X11 input paths. `-viewonly` disables X11 input forwarding as well as evdev input.

AV1, 4:4:4, 10-bit/HDR, Wayland and standalone TTY/KMS output are not implemented. The stream must keep the setup resolution: midstream visible or coded dimension changes are rejected **before** feeding the changed access unit to OMX. Restart streaming to change resolution. Hardware decode alone does not establish that a particular resolution or frame rate is sustainable in a complete network streaming session.

## System prerequisites

Install the matching RevyOS packages, not an upstream Debian FFmpeg without the TH1520 OMX patches:

- `th1520-vpu` (tested package version: 2.0.2).
- `libomxil-bellagio0` and the registered Hantro video decoder.
- RevyOS FFmpeg with `h264_omx` and `hevc_omx`, both exposing the `drm_prime` option.
- Loaded `vidmem`, `hantrodec`, `memalloc`, `vc8000` kernel modules; read/write access to the VPU device nodes.
- A working X11 session and GPU EGL driver. Zero-copy display additionally needs `EGL_EXT_image_dma_buf_import` and `GL_OES_EGL_image_external`.

Inspect the decoder options with:

```sh
ffmpeg -hide_banner -h decoder=h264_omx
ffmpeg -hide_banner -h decoder=hevc_omx
```

The backend refuses a same-named OMX decoder without the RevyOS `drm_prime` option. An explicit `-platform th1520` failure never silently selects a software decoder. The vendor `omxdectest` packaged in 2.0.2 can fail to start because of a missing `libplink.so`; it is not needed here.

## Build

```sh
sudo apt install cmake pkg-config build-essential \
  libavcodec-dev libavutil-dev libx11-dev libegl-dev libgles-dev libdrm-dev \
  libevdev-dev libudev-dev libopus-dev libasound2-dev libpulse-dev libsdl2-dev \
  libcurl4-gnutls-dev libssl-dev libexpat1-dev libavahi-client-dev uuid-dev

git submodule update --init --recursive
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DENABLE_TH1520=ON
cmake --build build -j4
```

No GStreamer development package or OMX development header is needed to build this backend. `-DENABLE_TH1520=OFF` excludes the dma-buf code and libdrm dependency; the usual FFmpeg/X11 and SDL backends remain available.

## Optional private FFmpeg lifetime repair

Long-session testing with the stock RevyOS `7:5.1.4-0+deb12u1revyos3` library reproduced approximately 24 MiB of RSS growth during ten minutes of 1080p60 DRM PRIME output. Its OMX wrapper allocates a DRM descriptor for each frame without tying it to the frame's release callback, repeatedly initializes the hardware frame context, and incorrectly frees AVBufferRef structures. Successful decoding and a stable fd count do not rule out this leak.

The [dependency patch](<patches/revyos-ffmpeg-omx-lifetime.patch>) fixes these ownership paths. The [private build script](<../scripts/build-th1520-ffmpeg.sh>) applies it to the pinned RevyOS FFmpeg commit `f86f86b3f7087b4e809a079371c4bc513d3d50f8` and builds only the libraries needed here:

```sh
sh scripts/build-th1520-ffmpeg.sh
LD_LIBRARY_PATH="$PWD/build/ffmpeg-fixed/lib" \
  DISPLAY=:0 ./build/moonlight stream -platform th1520 -codec h264 -1080 -viewonly <host>
```

This requires network access to fetch the matching source and, when absent, unpack the base OMX development headers. It does not install system packages, replace system FFmpeg, modify the dynamic loader configuration, or change VPU drivers. The private libraries are a minimal FFmpeg 5.1 build intended for this Moonlight binary, not a general-purpose system multimedia replacement. Keep this prefix private to the process.

The patch adds the `th1520_drm_lifetime_fixed` capability constant. In `auto` mode, Moonlight chooses DRM PRIME only when that marker is present; otherwise it conservatively selects NV12 **hardware** decoding. An explicitly forced `drm` mode remains available for dependency diagnostics and prints a warning when the fix is not detected.

## Run

Pair with your Sunshine/GameStream host and list its applications:

```sh
./build/moonlight pair <host>
./build/moonlight list <host>
```

From a terminal in the existing X11 desktop:

```sh
./build/moonlight stream -platform th1520 -codec h264 -1080 -fps 60 -app Desktop \
  -mapping third_party/SDL_GameControllerDB/gamecontrollerdb.txt <host>
./build/moonlight stream -platform th1520 -codec h265 -1080 -fps 60 -app Desktop \
  -mapping third_party/SDL_GameControllerDB/gamecontrollerdb.txt <host>
```

Replace `Desktop` with a name reported by `list`. When starting over SSH, set the display and authorization belonging to the existing local session, for example `DISPLAY=:0`; do not start a second X server. The process must be able to open that display and the VPU devices as the desktop user.

Output selection is controlled by an optional environment variable:

```sh
MOONLIGHT_TH1520_OUTPUT=auto ./build/moonlight stream -platform th1520 -viewonly <host>
MOONLIGHT_TH1520_OUTPUT=drm  ./build/moonlight stream -platform th1520 -viewonly <host>
MOONLIGHT_TH1520_OUTPUT=nv12 ./build/moonlight stream -platform th1520 -viewonly <host>
```

- `auto` (default): prefer DRM PRIME/dma-buf when the private lifetime-fix capability is detected; otherwise select NV12 hardware decoding. If DRM import/rendering fails, restart the **hardware** decoder in NV12 mode.
- `drm`: require dma-buf output. Import failure terminates display rather than concealing a fallback. This bypasses the conservative dependency check and warns when the lifetime fix is absent.
- `nv12`: force hardware decode with CPU-visible NV12 and GPU texture upload, useful for troubleshooting.

## Buffering, synchronization and recovery

The data path is:

```text
Moonlight Annex-B access unit
  -> avcodec_send_packet / h264_omx or hevc_omx
  -> Bellagio / th1520-vpu / VC8000D
  -> AVDRMFrameDescriptor (NV12 dma-buf planes)
  -> EGLImage / external GLES texture
  -> X11 window
```

The encoded packet is retained across FFmpeg `EAGAIN` and is retried only after receiving output. The vendor calls run on moonlight-common's decoder thread, not the network receive thread. The renderer has a one-frame mailbox: replacing an old **decoded** frame releases it immediately and does not discard encoded reference frames. An EGL fence retains the OMX output buffer until GPU sampling completes; drivers without usable fences use `glFinish()` instead.

NV12 upload honors per-plane stride and range/colorspace metadata. Window resizing updates the viewport. A separate public H.264/HEVC parser rejects stream dimension changes before sending them to the vendor decoder, whose dynamic-output reconfiguration does not safely respect retained frame references. Complete IDRs must carry SPS/PPS (and VPS for HEVC); partial configuration updates are conservatively rejected. This guard is not a complete malformed-bitstream validator. The DRM descriptor supplies plane offsets, pitches, object indices and modifiers; file descriptors remain owned by FFmpeg/OMX.

A bounded decode-pump error requests IDR and restarts the decoder on the rendering thread after returning queued/GPU-held frames. Frames are ignored until the next IDR. Renderer cleanup releases GPU references before destroying the decoder. Some vendor library operations can still block internally; the wrapper cannot impose a timeout inside proprietary OMX calls.

## Local integration test (no host required)

The optional smoke test drives the **production** decoder callback, frame mailbox and X11/EGL renderer, and checks that the mapped window contains non-black, varied pixels. It is not an end-to-end Sunshine test and is not a colorimetric comparison.

```sh
cmake -S . -B build -DBUILD_TH1520_TESTS=ON
cmake --build build -j4

ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=60 -frames:v 180 \
  -c:v libx264 -preset ultrafast -tune zerolatency -x264-params repeat-headers=1 \
  -f h264 /tmp/th1520.h264

DISPLAY=:0 LD_LIBRARY_PATH="$PWD/build/ffmpeg-fixed/lib" MOONLIGHT_TH1520_OUTPUT=auto \
  ./build/th1520-smoke /tmp/th1520.h264 h264 1280 720 60 1
DISPLAY=:0 MOONLIGHT_TH1520_OUTPUT=nv12 \
  ./build/th1520-smoke /tmp/th1520.h264 h264 1280 720 60 20
```

For HEVC, generate a raw HEVC file using `libx265 -tune zerolatency`, pass `h265`, and match the dimensions/frame rate. Use a test pattern (not an all-black movie) for the pixel check. Repeat count tests setup/stop/cleanup in the same process and prints fd/RSS information. GPU driver caches can grow during warmup; monotonically growing usage needs investigation rather than being dismissed as caching.

The CLI accepts `input codec width height fps [repetitions [seconds]]`; the default is three seconds per repetition. Short files are looped within the same decoder session for longer tests. Setting `MOONLIGHT_TH1520_TEST_THREADED=1` puts submission on a worker thread while the main thread owns EGL, matching the production thread model. `MOONLIGHT_TH1520_TEST_RENDER_DELAY_MS=100` deliberately stalls the UI to exercise bounded mailbox replacement:

```sh
DISPLAY=:0 LD_LIBRARY_PATH="$PWD/build/ffmpeg-fixed/lib" \
  MOONLIGHT_TH1520_TEST_THREADED=1 MOONLIGHT_TH1520_TEST_RENDER_DELAY_MS=100 \
  timeout 35s ./build/th1520-smoke /tmp/th1520.h264 h264 1280 720 60 1

# Ten-minute, single-component 1080p60 run using a matching 1080p input file:
DISPLAY=:0 LD_LIBRARY_PATH="$PWD/build/ffmpeg-fixed/lib" MOONLIGHT_TH1520_OUTPUT=drm \
  timeout 650s ./build/th1520-smoke /tmp/1920x1080.h264 h264 1920 1080 60 1 600
```

The CPU-only ownership/size checks do not open OMX or an X display. Prepare the three fixture sizes expected by the test:

```sh
for size in 1920x1080 1366x768; do
  ffmpeg -y -f lavfi -i testsrc2=size=$size:rate=60 -frames:v 5 \
    -c:v libx264 -preset ultrafast -tune zerolatency -f h264 /tmp/$size.h264
done
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30 -frames:v 5 \
  -c:v libx265 -preset ultrafast -tune zerolatency -f hevc /tmp/1280x720.hevc
./build/th1520-unit /tmp/1920x1080.h264 /tmp/1366x768.h264 /tmp/1280x720.hevc
```

These checks cover EAGAIN ownership/retry, polling versus EOS, fixed visible/coded dimensions, malformed configuration rejection, generic NV12-to-planar conversion, and unsupported codec rejection. The on-device results and remaining limitations are recorded in the [validation report](<TH1520-VALIDATION.md>).

A real host is still needed to validate network recovery, A/V synchronization, input, long-session latency and sustained network streaming. 4K has not been tested here.
